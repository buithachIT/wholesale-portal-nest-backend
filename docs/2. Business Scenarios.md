# 3. AUTHENTICATION

# ============================================================

## SC-001: USER LOGIN

Actor:

PURCHASER / ADMIN / ACCOUNTANT / SUPER_ADMIN

Preconditions:

- User tồn tại.
- User có email.
- User có password hợp lệ.

Main Flow:

1. User mở trang Login.
2. User nhập email.
3. User nhập password.
4. Client gửi login request.
5. System tìm user theo email.
6. System kiểm tra password hash.
7. System kiểm tra user.status.
8. System xác định roles.
9. System xác định permissions.
10. System tạo authentication session/token.
11. System trả thông tin user và quyền.
12. User được đăng nhập.

Alternative:

A1. Email không tồn tại.

→ Login failed.

A2. Password không đúng.

→ Login failed.

A3. User.status = suspended.

→ Không cho đăng nhập.

Result:

User được authenticated.

## SC-012: CREATE PRICING TIER

Actor:

ADMIN / SUPER_ADMIN

Preconditions:

- Variant tồn tại.
- Actor có permission PRICING_MANAGE.

Example:

1 - 19 → 0%
20 - 49 → 5%
50+ → 10%

Main Flow:

1. Actor mở pricing configuration.
2. Chọn variant.
3. Nhập min_quantity.
4. Nhập max_quantity nếu có.
5. Nhập discount_percent.
6. System validate range.
7. System kiểm tra overlap.
8. System kiểm tra tier không tạo khoảng quantity bị ambiguous.
9. System tạo pricing tier.

Alternative:

Nếu tier overlap:

→ Reject.

Nếu max_quantity < min_quantity:

→ Reject.

Nếu có nhiều tier cùng match một quantity:

→ Reject.

Result:

Variant có pricing theo quantity.

# 10. CREDIT ORDER

# ============================================================

## SC-019: APPROVE ORDER USING CREDIT

Actor:

ADMIN / authorized internal user

Preconditions:

- Order.status = pending.
- order.payment_method = credit.
- Actor có permission ORDER_APPROVE.

Example:

remaining_credit = 100m

Order = 70m

Main Flow:

1. Actor approve order.
2. System bắt đầu database transaction.
3. System lock company balance.
4. System kiểm tra remaining_credit.
5. remaining_credit >= order.total_price.
6. System giảm remaining_credit 70m.
7. System tạo credit_transaction:
   type = credit_reserved
   amount = -70m
   balance_after = 30m
8. System update order.status = approved.
9. Transaction commit.
10. System tạo notification.

Result:

Order được approve và 70m credit được reserve.

## SC-020: CREDIT LIMIT INSUFFICIENT

Actor:

ADMIN / authorized internal user

Example:

remaining_credit = 50m

Order = 70m

Main Flow:

1. Actor approve order.
2. System bắt đầu transaction.
3. System lock company.
4. System kiểm tra remaining_credit.
5. Phát hiện remaining_credit < order.total_price.
6. Transaction rollback.
7. Order không chuyển sang approved.

Result:

Order vẫn pending hoặc được xử lý theo cancellation/rejection policy.

## SC-021: TWO ORDERS USE SAME CREDIT

Initial:

remaining_credit = 100m

Order A = 70m

Order B = 60m

Main Flow:

1. A approve.
2. B approve đồng thời.
3. Database lock company.
4. Một transaction reserve 70m.
5. remaining_credit = 30m.
6. Transaction còn lại acquire lock.
7. Transaction còn lại kiểm tra remaining_credit.
8. Chỉ còn 30m.
9. Transaction còn lại bị reject.
10. Không tạo credit reservation cho order B.

Result:

Không thể reserve credit vượt hạn mức.

## SC-022: CANCEL ORDER WITH RESERVED CREDIT

Actor:

ADMIN / authorized user

Preconditions:

- Order.status cho phép cancel.
- Order đã reserve credit.

Main Flow:

1. Actor cancel order.
2. System kiểm tra order status.
3. System xác định reserved credit.
4. System bắt đầu transaction.
5. System lock company.
6. System hoàn reserved amount vào remaining_credit.
7. System tạo credit_transaction:
   type = credit_released
   amount = +reserved_amount
   balance_after = new balance
8. System update order:
   status = cancelled
9. System lưu:
   - cancelled_at
   - cancelled_by
   - cancellation_reason
10. Transaction commit.
11. System tạo notification.

Result:

Credit được giải phóng và order bị cancelled.

## SC-024: ACCOUNTANT APPROVES PAYMENT

Actor:

ACCOUNTANT

Preconditions:

- Payment.status = pending.
- Actor có PAYMENT_APPROVE.

Main Flow:

1. Accountant mở pending payment.
2. Kiểm tra giao dịch ngân hàng.
3. Chọn Approve.
4. System bắt đầu database transaction.
5. System lock payment.
6. System kiểm tra payment vẫn pending.
7. Update:
   - status = approved
   - approved_at = now()
   - approved_by = accountant
8. Xác định allocation.
9. Allocate payment vào order nếu có.
10. Update order payment status.
11. Nếu có overpayment:
    - tăng wallet_balance
    - tạo wallet_transaction
12. Commit transaction.
13. Sau khi commit, tạo notification.

Result:

Payment được xác nhận và có thể được sử dụng để thanh toán.

## SC-028: ALLOCATE PAYMENT TO ORDER

Example:

Payment = 100m

Order = 70m

Preconditions:

- Payment.status = approved.
- Actor có PAYMENT_ALLOCATE.

Main Flow:

1. Accountant chọn payment.
2. Chọn order.
3. Nhập allocation = 70m.
4. System kiểm tra allocation <= payment remaining amount.
5. System kiểm tra allocation <= order outstanding amount.
6. System tạo order_payment.
7. System tính allocated amount mới của order.
8. Order.payment_status = paid.
9. Payment còn 30m.
10. 30m được phân bổ tiếp hoặc xử lý thành wallet theo policy.

Result:

Order được thanh toán đủ.

↓

↓

2. User phải active.
3. Permission phải được kiểm tra.
4. Company user chỉ được truy cập dữ liệu của company mình.
5. Internal user chỉ được truy cập phạm vi dữ liệu theo permission.
6. Product là catalog hiện tại.
7. Product có thumbnail.
8. Variant có nhiều images.
9. Variant có stock nhưng không có inventory/warehouse module.
10. Variant chỉ có base_price, không có old_price.
11. Pricing tier quyết định discount theo quantity.
12. Order item lưu snapshot dữ liệu tại thời điểm order.
13. Order lifecycle độc lập với payment lifecycle.
14. Payment status độc lập với order status.
15. Logistics lifecycle độc lập với order và payment lifecycle.
16. Credit reservation phải transactional.
17. Credit release phải transactional.
18. Payment phải approved trước khi được sử dụng để allocation.
19. Payment có thể phân bổ cho nhiều orders.
20. Một order có thể nhận nhiều payments.
21. Overpayment được chuyển vào wallet.
22. Wallet có ledger riêng.
23. Credit có ledger riêng.
24. Financial operation phải atomic.
25. Balance quan trọng phải được bảo vệ khỏi race condition.
26. Stock update khi tạo/chốt order phải tránh overselling.
27. Một order có thể có nhiều logistics.
28. Carrier suspended không được dùng cho logistics mới.
29. Carrier webhook phải được lưu raw payload.
30. Webhook processing phải idempotent.
31. Notification chỉ phản ánh business event, không thay thế business data.
32. Notification chỉ được tạo sau business transaction thành công.
33. Ledger transaction không được sửa/xóa tùy tiện.
34. Sai lệch tài chính phải được xử lý bằng adjustment transaction.
35. Retry không được tạo duplicate business effect.
36. Database constraint và application validation cùng bảo vệ business rule.
37. Không xây dựng inventory/warehouse management.
38. products.thumbnail là ảnh đại diện của product.
39. product_variant_images là gallery của variant.
40. Order history không được phụ thuộc vào catalog hiện tại.
